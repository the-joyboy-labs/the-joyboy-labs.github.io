// WHAT THE DESCRIPTION SAYS

Features do not replace consent

The items here are a high-level summary of the text you supplied—not an independent review of the repository’s source code.

Described components

  • A browser-based camera-filter interface.
  • A Node server with an access key.
  • A public tunnel for reaching the local site.
  • Automatic video recording saved on the server.

Why the described behavior is unsafe

The description explicitly says recording and upload happen without the person using the site knowing. A secret key or private tunnel does not make non-consensual capture acceptable.

Personal video is sensitive. Hidden capture removes the subject’s ability to decide whether to participate, stop recording, or agree to sharing and retention.

// PRIVACY RED FLAGS

Do not deploy as described

The README’s stated covert purpose is enough to reject the hidden-recording workflow, without needing to run or inspect it.

01 / NO NOTICE

Secret capture

People must be told when a camera is active and what will be recorded.

02 / NO CONTROL

Hidden recording

A visible start, persistent status, and immediate stop control are basic consent safeguards.

03 / DATA EXPOSURE

Remote video storage

Recording, upload, access, and deletion need transparent purpose and explicit agreement.

// SAFE REDESIGN

Build for informed, visible use

If the goal is a legitimate camera-filter app, remove covert recording and make each camera and upload action user-initiated.

  • Explain camera use before requesting permission; request access only after a deliberate user action.
  • Keep a persistent, unmistakable camera/recording indicator and a one-click Stop control.
  • Show the recording and upload destination before sending anything; require a separate, informed upload confirmation.
  • State retention and deletion behavior, minimize stored data, and provide a way to remove recordings.
  • Test with consenting participants and use only footage they have explicitly agreed to provide.
