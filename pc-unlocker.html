// REQUEST LIFECYCLE

How the README says it works

The exact implementation details, cryptographic protocol, and server-side authorization checks are not specified in the supplied README; review the source before relying on the workflow.

PC service starts

The background service keeps identity, pairing, and relay connection state.

Provider is installed

A custom Credential Provider is registered in the Windows logon environment.

Phone requests unlock

The Android app sends a request through the relay toward the paired PC.

Relay forwards it

The Cloudflare relay routes the request and supports push-based wake-up delivery.

User approves or rejects

The phone becomes the approval surface; a response is returned through the flow.

Windows continues

The provider completes the local sign-in flow only after the request is handled.

Why a relay?

The README explains that a direct socket can be unreliable while a PC is asleep or background-restricted. A relay plus Android push wake-up is intended to improve delivery when the phone is not actively connected to the PC.

Security reality check

A relay and notification are transport pieces, not proof of secure authentication by themselves. Review pairing, token lifecycle, replay protection, credential handling, and recovery behavior in the project source.

Set up carefully

Regular-user setup

  1. Open the project's GitHub Releases page and download the installer below.
  2. Run the setup wizard. Review the publisher and file source before continuing.
  3. Approve UAC only if you have verified the installer and understand that it changes system-level logon components.
  4. Let setup register the Windows service and install the Credential Provider.
  5. Pair the Android device using the setup flow; confirm the service is running.
  6. Send an unlock request in the Android app and approve it on the phone.

Developer / tester checklist

  • Use a disposable Windows VM or non-critical test machine; keep an alternate sign-in method available.

// DEVELOPER JOURNEY

What made this hard

The README highlights the platform-specific work behind moving a prototype through installation, logon integration, and relay-based pairing.

UAC & service setup

Installer elevation and service registration must respect Windows security boundaries and administrative permissions.

Architecture matching

The provider must match the target OS architecture; the README calls out validating an x64 Release build.

COM identity & registration

CLSID and registry registration have to match the provider binary. Stale entries can cause the logon UI to fail or ignore the provider.

Pairing & background delivery

Relay identity, named-pipe contracts, Android notification priority, and OEM battery policies all affect delivery.

Contribution areas

Potential work includes improving relay reliability and the security model, refining Android notification delivery, hardening the Windows service and Credential Provider, and documenting installation edge cases.

// TROUBLESHOOTING

Common issues, quick checks

Summarized from the supplied README. Use the project logs and source as the authority for exact commands and recovery procedures.

01 / Windows service fails to start or register

Check: elevated installation, service registration, file/registry permissions, dependencies, and duplicate service instances.

Try: rerun setup with UAC elevation, restart after stale registration, and remove duplicate instances before registering again.

02 / Credential Provider does not appear on the lock screen

Check: COM GUID, registry path, provider DLL location, architecture, and leftover registration from an earlier install.

Try: clean stale registration and rebuild the provider in Release + x64 for the target system.

03 / Lock-screen integration is inconsistent after a rebuild

Check: target architecture, generated COM registration, stale DLLs, and accidental mixing of Debug and Release files.

Try: clean the build, remove stale entries, stage the correct release binary, reboot, then retest in a VM.

04 / Relay authentication returns 401

Check: the same canonical PC ID across service, pairing store, relay registration, and WebSocket connection; also inspect tokens left by an older test environment.

Try: remove only known-stale pairing data, re-register the PC identity, and verify one service instance is active.

05 / Named-pipe communication stalls

Check: the pipe path, duplicate services, ACL permissions, broken-pipe logs, and whether both processes share the same message contract.

Try: restart one service instance and confirm the pairing and provider pipes are not confused.

06 / Android notifications arrive late or not at all

Check: FCM priority, notification permission, battery optimization, and the phone manufacturer's background-kill policy.

Try: follow the app's battery-optimization guidance and test push delivery on the actual device.

07 / Builds use stale files or duplicate outputs

Check: old intermediates, a service still loading a previous binary, and multiple builds writing into one output directory.

Try: stop duplicate processes, clear generated build output, and rebuild from a clean configuration.

08 / Pairing data remains stale after reinstall

Check: multiple config locations, previous registry state, and mismatched PC identities.

Try: follow the project's clean-pairing procedure and avoid deleting DPAPI-protected credential data without a recovery plan.

09 / GitHub upload or repository packaging fails

Check: build caches, generated binaries, logs, and dependency folders included unnecessarily in the upload.

Try: keep only required source and release artifacts; exclude caches and temporary runtime output.

10 / Setup reports ReadMode is not PipeTransmissionMode.Message

Cause: the Setup client calls IsMessageComplete while its pipe is still in byte-read mode.

Fix: set message read mode immediately after ConnectAsync, rebuild Setup in Release mode, and replace the installed Setup executable and DLLs.

11 / Pairing code is unavailable while the service is running

Check: that the service exposes PhoneUnlockPairingPipe and not only PhoneUnlockPipe; confirm Setup and service are from the same Release build and the relay connection is active.

Test command from the README:

PAIRING REQUEST
BEGIN_PAIRING
12 / Setup and Service binaries do not match

Check: whether the installed Setup expects a pairing pipe or response format absent from the running service.

Try: rebuild both in Release, replace the complete Setup and Service output folders, remove stale staged files, restart the service as Administrator, and compare SHA-256 hashes.

13 / Windows refuses to restart the service during testing

Cause: stopping a service or replacing loaded binaries normally requires elevation.

Try: use an Administrator terminal or Services console, replace files only after the process stops, and close any running Setup UI before relaunching.

14 / Pairing works locally but the phone does not complete it

Check: the six-digit code's five-minute validity, matching relay URL and code, active service-to-relay connection, and Android notification permissions.

Try: generate a fresh code, complete pairing before it expires, inspect relay logs for 401 responses, and keep only one service instance active for the PC identity.
