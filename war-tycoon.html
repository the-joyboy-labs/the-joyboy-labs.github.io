// HOW THE LOGIC WORKS

Eight cooperating routines

Open a topic for a concise, README-derived explanation. Behavior depends on visible interface text, loaded objects, and the execution environment.

01 / Startup and lifecycle

The script obtains the local player and PlayerGui, builds a draggable ScreenGui, removes a previous HUD, disconnects stored connections, and increments a shared run ID. Background loops check that ID so an older run can stop when replaced. The buyer starts OFF.

02 / Cash Collector and purchase scan

The scanner looks through visible BillboardGui and SurfaceGui text in loaded workspace and player UI, resolves an adornee/parent to a part, and checks ownership clues. It keeps a still-valid selected collector or chooses a nearby candidate; its position is remembered as lastCollectorPos.

Cash is read from likely leaderstats values (cash, money, coins) or visible dollar-formatted HUD text. Price parsing supports plain values and k, m, b, and t. Excluded labels include exchange-related purchase text. Affordable buttons are sorted cheapest-first; after each visit, disappearance of the sign or a balance change is used as a success clue. Failed buys are retried up to the configured attempt count.

03 / Rebirth target scan

The scanner looks for short interface labels with a number followed by “Rebirth,” filters likely information signs and long instructions, and checks base ownership or proximity to the remembered collector. A nearby pad can optionally be required.

Targets are ordered from the smallest rebirth number. Off-screen targets may be remembered while the script requests streaming and scans again. Failed targets can be temporarily skipped; the accepted ceiling is 12, while 0 disables this automation.

04 / Completion and confirmation safeguards

A local PlayerGui reader looks for “Completion” and a percentage in one label, a shared UI container, or a nearby percentage label. At 100%, one action is armed for that cycle. It waits for Auto Buyer ON, idle delivery/airdrop/barrel routines, and readable cash of at least $500,000 (the amount shown in the supplied confirmation screenshot).

  1. Hold E for two seconds and release.
  2. Find a visible Rebirth confirmation with a readable Cost:.
  3. Re-check cash against the dialog cost; cancel when available and wait if funds are insufficient.
  4. Click Confirm only after the amount is met; increment a positive target only after the dialog closes, capped at 12.

If the dialog, cost, or close event cannot be identified, the target is not incremented. A target of 0 or an empty field stays disabled. The completion action rearms after progress drops below 100%.

05 / Oil barrel and airdrop detection

Floating BillboardGui text containing Oil or Airdrop plus a distance is used to identify targets. Distance suffixes such as k, m, and b are parsed; a cooldown helps avoid repeated triggers. The manual HUD test requests the same handling sequence.

After pickup, the associated barrel object is remembered because its floating label may change. A carried or tracked barrel becomes pending delivery and blocks unrelated travel until the delivery attempt is resolved.

06 / Oil Exchange route and fallback

With a barrel pending, the script first returns by flight to the remembered Cash Collector area to help stream the base back in. It then searches for exchange clues in labels, prompts, and part/model names.

The price-bearing “$100,000 PARTS $100,000 OIL EXCHANGE” sign is treated as a purchase pad, not the physical exchanger, and price-bearing purchase cues are filtered. If no usable exchanger is found, it searches for a floating “Resource Collection … studs” marker and ranks candidates by 3D distance from the remembered collector, not by the changing UI distance. If neither marker is usable, delivery may remain unresolved.

07 / Death and dropped-barrel recovery

A character-death watcher records a tracked/carried barrel and marks recovery pending. After respawn, it searches for the floating Oil distance label, preferring a target near the last known position. Recovery and exchange work take priority over rebirths and construction-button trips; pending state is cleared only after delivery has been attempted and the dropped label is no longer detected.

08 / Movement and input safeguards

Ordinary target travel uses the teleport helper only when there is no pending/carried barrel. During delivery, flight is restricted to the intended collector/exchange route. Flight speed defaults to 50 and slows near the destination.

The script intentionally does not move equipped Tool objects into the Backpack; it releases a stuck mouse input when enabled instead, avoiding the reported ACS weapon-reference failure associated with reparenting an equipped tool.

// TROUBLESHOOTING

Common checks

Summarized from the supplied README. Exact behavior can change with game updates, UI wording, streaming state, or executor compatibility.

No “Cash to collect” found

Wait for the base and collector label to load. The scanner relies on visible UI text and ownership clues.

Can't read money

Confirm cash is exposed in a likely leaderstats value or visible as dollar-formatted HUD text; otherwise the scan may have no reliable balance.

Oil Exchange not found / barrel still carried

Check whether a usable exchanger or Resource Collection fallback marker is streamed in. The fallback may not be the correct deposit point; the README says delivery can remain unresolved if no valid interaction target is recognized.

Dropped barrel is not recovered

After respawn, the recovery scanner expects a floating Oil distance label. If it is absent, the target may not be found.

Completion stays at --%

The local PlayerGui reader expects recognizable completion text. A server-only value or differently worded interface may not be detected.

100% action waits instead of pressing E

According to the README, Auto Buyer must be ON, delivery/airdrop handling idle, and cash readable at or above $500,000 before the confirmation flow begins.

Rebirth confirmation is not clicked

The script expects a visible Rebirth dialog with a parseable Cost label and sufficient cash. If the dialog or button differs, it leaves the target unchanged.

Controls do not respond

Confirm that the buyer is ON for automated actions and that the environment supports the client APIs the script expects. These APIs are not standard Roblox Studio script features.

Third-party client automation

The README names APIs such as loadstring, game:HttpGet, getgenv, VirtualInputManager, and optional input/prompt helpers. These are not standard capabilities for ordinary Roblox Studio scripts; support varies by environment.
